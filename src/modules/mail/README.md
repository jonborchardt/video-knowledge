# mail

The system's conversation with a person by email: one outbox (every mail the system sends, questions included), one received store (every mail that came back, correlated once to what it answers), an archive, and the verbs `ask`, `send`, `fetch`, `questions`, `test` (`npm run mail`). Two kinds of interaction ride the same records without sharing semantics: **general communication** (`ask`: a question in ordinary language; the reply comes back as the person's own words for the calling agent to reason about, never read by the module as authorisation) and **formal authorisation** (release, scheduling, go-live, paid links, topic approval, article corrections: orchestration's request mails and reply grammar, applied through their own verbs with their request ids and signed manifests).

- `core/` is the extraction-ready core (plan Revision log 17 to 19): it imports nothing outside itself but `node:*` and the mail packages (`selfContained` in `tests/boundaries.json`, enforced by `tests/boundaries.test.ts`), is configured by one injected `MailConfig` and one `MailTransport`, and knows `kind: string` and `meta` only, never a request id, a topic, a story or a workflow. `core/README.md` (Task 7) says how to copy it elsewhere.
- The Commonwealth adapter around it (`cor.ts`, Task 3) turns `automation.json` and `.env` into the core's configuration; `cli.ts` is `npm run mail`; `index.ts` is the read API.
- Files: `core/io.ts` (the few file helpers, copies of `src/shared/io.ts`'s), `core/mutex.ts` (the prepared-directory lock: held/ exists only by the atomic rename of a directory holding its owner marker, recovered only from a dead pid, never by age), `core/types.ts` (`MailConfig`, `MailTransport`, `OutMail`, `InMail`, `OutboxEntry`, `Answer`, `Correlation`), `core/thread.ts` (`ownText`, `address`, `questionIdsIn`, `correlate`), `core/transport.ts` (`messageIdOf`, `fileFakeMail`: the file-backed fake mailbox real processes share in tests).
- `core/outbox.ts`: the record-before-send outbox, the per-message send claim, the one migration (`init`), `validateSend`. Every mutation runs under the mutex with no network call inside; delivery is at least once. `npm run mail -- init|send` (`cli.ts`); `cor.ts` supplies the paths, addresses, kinds, legacy files and transport.
- `core/received.ts`: the one inbound pipeline. `fetchInto` is the only reader of the mailbox, `received.json` holds the only cursor (with UIDVALIDITY as a string); each message is recorded once and correlated once, when it is recorded; a question collects its answers there; the source stays in `received/<sha12>.eml`. `core/transport.ts` holds the real transport and `FakeMail`. `npm run mail -- fetch`; the tick reaches it through `pollInbox`, which reads the store and resolves a thread to its request (`originOf`, orchestration's).
- Retention (`archive` in `core/received.ts`, run by every fetch): only completed records move to `archive/<YYYY-MM>.json` after `retentionDays`. A question is completed when answered and acknowledged, or closed; an unanswered one, or one answered but not accepted, stays live at any age. The host's `keepReceived` keeps what it has not processed (here: a reply to a request the inbox adapter has not handled). Lookups and correlation span the archives.
- Live continuation and durable recovery: a running agent gets the answer when `ask` exits; once it has ended the answer is still recorded, and the digest, the live page's owner list and `questions --unseen` show it, but nothing resumes the work by itself. Channel choice is the caller's (`docs/OPERATIONS.md`), never this module's.
- Read API (listed under `mail` in `tests/boundaries.json`): `ownText`, `address`, `questionMail`, the types, and the adapter reads `readCorOutbox`, `readCorReceived`, `filterCorOutbox`, `unsentCorOutbox`, `corResendDue`, `corMailDir`, `mailConfigFromEnv`, `openCorQuestions`, `COR_REPLY_GUIDES` (the first lines of every mail, by kind).
- Tests: `tests/{mutex,thread,correlate,outbox,init,send-cli,received,fetch-cli,transport,ask,ask-cli,standalone}.test.ts` (`mutex-child.ts` is the process the mutex tests spawn; `consumer-child.ts` is the consumer the lifecycle test in `ask-cli.test.ts` runs: ask, reply, act once, acknowledge, report, with a kill between the action and the acknowledgment; `primitives-experiment.ts` is the by-hand measurement behind the lock).
- Decisions about a question, and one-way mail: `close`/`reopen` (`core/ask.ts`) append `{at, by, action, note}` to the entry's `history`; a closed question is complete and out of every open list, and a reply after closure is kept and shown but never reopens it. `acknowledge` takes a note saying what the answer caused. `npm run mail -- report` is a one-way mail through the outbox (kind `report`, guide "NO REPLY NEEDED"), never a question. The transport's verdict (`SendResult`: accepted, rejected, response) is kept on the entry as `smtp`; a rejected recipient is a failed attempt, never `sentAt`. A mail from mailer-daemon or postmaster is a bounce (`why: 'bounce'`), listed by `unmatched` and counted by `questions`, never an answer.
- `core/ask.ts`: a question is an outbox entry with an expected reply. Status is derived (`statusOf`: unsent, failed, awaiting, unattended, answered, closed, with `late` and `seen`). A timeout stops the waiter, never the question. Receipt and acknowledgment are separate: an answer is durable once a fetch records it and stays `--unseen` until the consumer runs `questions --ack`, so a caller that dies holding the answer loses nothing. A follow-up (`--reply-to`) reuses its parent's subject, because mail clients thread by subject too, so an id-only reply to a question with follow-ups is ambiguous rather than the parent's.

## Extraction

`core/` is ready to copy into another TypeScript project; it is not extracted. `core/README.md` says how to use it elsewhere. What stays here is the adapter: `cor.ts` (paths, addresses, kinds, legacy files, `keepReceived`, the transport from `.env`), `cli.ts`, `index.ts`. Three checks hold the line: `selfContained` in `tests/boundaries.json` (imports, never allowlistable), `npm run typecheck:core` inside `npm run check` (compiles the core and its fixture with `rootDir` set, so anything reached outside the module fails), and `tests/standalone.test.ts` (the core through its public index with its own configuration and a fake transport, plus a scan of the core sources for this project's vocabulary).
