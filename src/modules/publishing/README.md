# publishing

Publishing owns YouTube only: uploads, release approvals, scheduling, go-live, read-back and verification, recorded in the per-story ledger. Social (X and others) is a separate Milestone 2 module and never part of this one.

- Inputs: `video/review/review.json` and the review package of the story (the build report through shared `build-report`), `video/upload-session.json`.
- Outputs: `publish.json` per story: `events` are written only by the CLI, `metadata` may be hand-edited and is validated at build.
- CLI: `npm run publish -- <verb> <topic> <story-id>` (`cli.ts`). Hand verbs: `show`, `uploaded`, `approve`, `accept-draft` (the draft acceptance `video final` records, run by it as a child; refused for an `automated:` actor unless `automation.json` `review.draft` is `agent` and the actor is the draft-review agent's, `automated: draft-review by <model> session <id>` (`DRAFT_REVIEW_ACTOR`); refused on an output already approved for publication: live, scheduled, or its release build approved; `--dry-run` runs those checks only and writes nothing), `request-changes` (sends the current build back with placed notes), `thumbnail`, `scheduled`, `published`, `updated`, `failed`, `correct-actor` (who really ran a `verified` event that names someone else: an `actor-corrected` event beside it, never a person's act reattributed), `unpublished`, `retracted`, `add`. API verbs: `auth`, `upload` (always private), `push`, `go-live`, `sync`, `verify`.
- Draft acceptance: `recordApproved({ accepted: true, build })` writes the same `approved` event as an approval, but only for the draft-voice build the build on disk replaced (`replaces` in its build report, written by video QA, with `narrationPublishable: false`): a draft is a voice, never a review.json label, which flips to release when music is cleared under the same sha. The build on disk, any build uploaded as a release or narrated under commercial terms, an unknown sha, a missing `build` and any generic output are refused; there is no hand route on the draft on disk (a draft is accepted by running `npm run video -- final`). An accepted build is only ever a draft voice, and every public path refuses a draft, so an acceptance never authorises publication.
- Draft review policy (spec §7.3): the CLI reads `review.draft` from `automation.json` for `accept-draft` and `request-changes` only. Under `person` and `shadow` both take a person's name; under `agent` the draft-review agent's actor may accept a draft build or send one back with placed notes, never a release build. Release approval (`approve`), `go-live`, `scheduled`, `published`, `unpublished` and `retracted` read no policy and refuse every `automated:` actor.
- A fixture topic's output (spec §5.8, D20): `go-live` sends `unlisted`, never `public`, on the same `approved` as any release; `sync` and `verify` read unlisted as its published state; the `published` event carries `visibility: unlisted` (a public release records none). `storyOutputs` still shows no public video for it, so the production site never embeds it.
- Channel credentials per commission (register D18, phase 3): `loadCredentials(root, env, { commission })` (`youtube.ts`) reads `YOUTUBE_OAUTH_CREDENTIALS_PATH_<KEY>` when set (`credentialsVar(key)`), else the shared `YOUTUBE_OAUTH_CREDENTIALS_PATH` or `.youtube-token.json`; the CLI resolves the commission from the topic for every API verb, and `auth [--commission <key>]` stores the refresh token in that commission's file (`saveRefreshToken`). A single channel keeps working with no new variable.
- The approval request (spec §7.2): `request --channel email` writes `approval-requested` on the main output binding `video/review/release-manifest.json`'s `releaseSha` (packaging's file, read through `MANIFEST_FILE` in shared io and the shared `ReleaseManifest` type), with `request: rq-<12 hex>` (`src/shared/request.ts`: an HMAC over the sha and the time with `APPROVAL_SECRET` from `.env`, at least 16 characters), `outputs` in publication order, `expiresAt` (`automation.json` `approvals.expiresDays`) and `channel`. `requestProblem` refuses unless the manifest is current (every packaged output in it, every metadata sha and the article's release sha as now), every output is uploaded private with the manifest's build, pushed, verified since its last send, a release build, and none is live or scheduled. Idempotent on an open request for the same release; a different release voids the open one (`decided`, `verdict: void`); `--renew` after expiry writes one renewal (`decided`, `verdict: expired`, then the new request), a second expiry is a person's (`request-expired`). `message-sent` records the request mail's Message-ID. `decide --request <id> --by <name> --verdict ok|schedule|changes [--at <ISO>] [--note ... [--at-seconds n] [--scene id] [--sentence id]]* [--paid <cta id>]* --via <channel:messageId>` (`decide.ts`, phase 3) applies a person's decision against the exact manifest the request bound (`decideProblem`: unknown, expired or decided request, a moved `releaseSha`, an automated name, a schedule under `approvals.scheduleLeadMinutes`, a paid id outside the manifest), every step idempotent and `decided` last: each `--paid` link through `npm run links -- cta approve` and `npm run video -- package` as children (the sha stands, the metadata sha moves), one `approved` per output of the group (`via.checklist: asserted-by-email`), `push` when behind, `sync` (a go-live that died after YouTube's update is found public here), then the video's `go-live` now or at the time with `via`; the Shorts are approved here and go live from the tick after the video. A `changes` verdict records `changes-requested` on the video (a note starting `short:<slug>` on that Short). `openRequest(ledger, releaseSha?, now?)` and `requestOf(ledger, id)` read them (read API).
- Files: `publish.ts` (ledger and verbs), `uploader.ts` (API verbs), `youtube.ts` (the one API client), `verify.ts` (read-back checks), `outputs.ts` (the public video view of a ledger).
- Inspect: no; the board reads `outputStates` and the other names `index.ts` exports.
- Public API (`index.ts`): ledger readers and types, `outputStates`, `currentBuild`, `mainOutput`, `storyOutputs`, `seekUrl`, `uploadProblem`.
- Read API (read-only, nothing written; listed under `publishing` in `tests/boundaries.json`): `loadLedger(topic, storyId)` reads `publish.json` and returns the validated ledger or null; `mainOutput(ledger)` is the video's main output id, computed from a ledger already read; `uploadProblem(metadata)` is the YouTube limits check on title, description and tags, a pure function; `storyOutputs(topic, storyId, root)` is a story's live video and Shorts from its ledger and review package, plus `releasing` (plan B: the main output's uploaded video once a person decided `ok` for its build and before it is public; `video` keeps meaning a `published` event, and only the content graph, the matter page's embed and `liveClaimIds` read `releasing`); `decidedOk(output)` is that decision (the latest `decided ok` whose request approved the last upload's build, while the approval still holds), or null; `currentBuild(dir)` reads the packaged build (mp4 sha and draft or release status) from `video/review/review.json`, or null; `openOutput(topic, storyId, { output, root })` reads one output's ledger entry, build, composed metadata and state (it refuses a missing output or folder, never writes; the verbs write through their own `write`); `publishPath(topic, storyId)` is the ledger's path; `emptyLedger(video)` is a new ledger value, not saved; `noteLine(note)` and `stampOf(seconds)` format a review note and an m:ss time; `seekUrl(video, seconds)` is a watch URL that starts at a time, pure; `renderStep(step)` renders an output's structured next step (`OutputStep`: `verb`, `actor` (`person`, `automation`, `youtube`, `none`), `args`, `retryable`, `blocked`, `failed`) to the line a person reads, the one both `publish show` and the board print; the types `Ledger`, `PublishEvent`, `ReviewNote`, `OutputState`, `OutputStatus`, `OutputStep`, `PublicVideo`, `UploadMetadata`. The verbs (`recordApproved`, `recordChangesRequested`, ...) are not in it: the review page runs them as `npm run publish` children.
- Shared: `Refusal` lives in `src/shared/refusal.ts`; the stories file is read through shared io.
