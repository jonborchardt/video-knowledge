# video-knowledge

Topic knowledge stores (claims from YouTube videos and blog posts, judged against studies) published as an Astro site. Each topic lives in `topics/<topic>/` (`topicDir()` in `src/lib/io.ts`); a cite (`<topic>/sources/<file>.txt#L10-L24`) is relative to `topics/`, so the cite text in the store, reports and approved scripts never carries the folder. The workflow for adding a topic is in README.md; the agent contract for the watcher CLI is `.claude/skills/watcher/SKILL.md`; the briefs handed to parallel agents are `scripts/briefs/`.

## Commands

- `npm run validate` before committing: typecheck, lint, format check, build, tests. CI runs the same and deploys `dist/`.
- `npm run quality` is the web-quality gate for site changes: build, the static gate and the browser suite (one page per template, Chromium); `-- --audit` runs every page in Chromium, Firefox and WebKit plus `npm audit`. Results in `.web-quality/`. Browsers: `npx playwright install chromium firefox webkit` once.
- `npm run format` fixes formatting (prettier with astro + tailwind plugins).
- `npm run report` regenerates `topics/<topic>/report.json` and keeps `topics/<topic>/public-record.json` (exhibit numbers that never renumber, and a revision for each claim whose finding label or verdict changed; it prints those that need a note). It needs the watcher checkout (`../retire-sim/watcher` or `$WATCHER_DIR`), so it only runs locally; commit the result, the site is built from it. `-- seed [topic]` numbers exhibits without the watcher; `-- note <topic> <claim> "<note>"` explains a revision.
- `npm run watcher -- <cmd> --store topics/<topic>/store` runs the watcher CLI.
- `npm run links -- freeze` writes `public-urls.json` (every indexed page in `dist/`; run after `npm run build`, commit it); `check` requests every outside URL the built site and the committed descriptions link (local and networked, never in CI; exit 1 on a failure).
- `npm run stories -- discover <topic>` regenerates `topics/<topic>/stories.json` (story candidates with their evidence audit), merging `topics/<topic>/story-review.json` if present; it reads the report and store, so it runs anywhere. Commit the result. `validate <topic> <assertions.json>` is the evidence gate. The review file is the agent's semantic pass (`scripts/briefs/stories.md`): applicability of each verdict to a sentence, coherence and pruning of each candidate, viewer-facing framing.
- `npm run script -- run <topic> <story-id>` drives the script stage in `topics/<topic>/scripts/<slug>/`: `package` builds the evidence package from stories.json and the store, `validate` checks `script.json` (written by an agent from `scripts/briefs/script.md`) and merges `script-review.json` (written by a different agent from `scripts/briefs/script-review.md`), `storyboard` fills and checks `storyboard.json` (from `scripts/briefs/storyboard.md`); `show` prints the reviewer's sheet; `lock --approved-by "<name>"` writes `release.json` once validation is `passed`, the storyboard `ok` and a render check it re-runs is ok with every bespoke graphic approved; it refuses any approver containing a `<...>` placeholder. Commit the directory.
- `npm run article -- validate|show|lock|correct|reaffirm <topic> <story-id>` drives the companion article in `topics/<topic>/scripts/<slug>/` (`src/lib/article.ts`, `article-validation.ts`): `validate` checks `article.json` (the script checks over its sentences, plus coverage, metadata, tables, figures and overlap with the narration) with `article-review.json` against the story's evidence package, writing `article-validation.json` and `article.md` and printing `RESULT:`; `show` prints `article.md`; `lock --approved-by "<name>"` writes `article-release.json` (the snapshot the site renders) once a review exists and a fresh validation passes; `correct --approved-by "<name>" --note "<note>"` releases changed text and appends an article revision (the changed sentence ids and the note) to `public-record.json` (once: a re-run finds it there); `reaffirm --approved-by "<name>" --note "<why unchanged>"` keeps a stale article's unchanged, passing text, adding a history entry and moving the release date to today (no public-record revision). The reviewer approves the headline, SEO title, headings, tables and figures by unit id at the fingerprint `show` prints, as sentences. Refusals exit 2 and write nothing.

- `npm run video -- spike <topic> <story-id>` renders `topics/<topic>/scripts/<slug>/video/segment.mp4` from `video/render.json` (scenes, voice, cues, bespoke kinds, options, chapters): narrate (edge-tts draft or openai commercial, cached per sentence), timeline (measured audio, not the word-count estimate), render (Remotion, one cached chunk per scene, concatenated, narration track laid down with loudnorm, the soundtrack from `video/music.json` mixed under it into `video/mix.json`), qa (build-report.md, frames/, contact-sheet.png). `render --scene sc17` renders one scene with audio into `video/scenes/`. `package` writes the private review package to `video/review/`. `preview` opens the Remotion studio. Commit the JSON and the report, never the media.
- `npm run video -- final <topic> <story-id> --approved-by "<name>"` is the release build: development always narrates with `edge` (draft only); once a person accepts the draft package, `final` re-narrates the same words with `azure` (the same neural voice under commercial terms, keys in the gitignored `.env`), then re-runs timeline, render, qa and package in place. It refuses a story the board does not say is `packaged`, a placeholder approver, or a failed QA. The approver is recorded in the build report's command line. A cleared build packages as the release build (`status: release build` in `review.json`: `<slug>.mp4`, the real title, no private banner, voice line or draft-voice check); a draft build keeps the private review package. Both are the same `video/review/` folder and the board tells them apart by the report's clearance.
- `npm run video -- init <topic> <story-id> [--force]` drafts `video/render.json` from the storyboard (never overwrites without `--force`); `check` writes `video/render-check.json` (renderability, diagrams without a graphic, each bespoke graphic's approval in `video/visual-review.json` at its key); `frames --scene <id>` renders one scene on its own into `video/frames/<id>-start|mid|end.png`. QA, spike and a full render end with `RESULT: PASSED` or `RESULT: FAILED (...)`.
- `npm run board -- next <topic> <story-id> [--json]` prints the board's stage, next step, steps and halt kind for one story; `.claude/skills/produce/SKILL.md` (`/produce`) loops on it from `ready` to `packaged`.
- `npm run publish -- <verb> <topic> <story-id> [--output <id>]` keeps the publishing ledger `topics/<topic>/scripts/<slug>/publish.json` (`src/lib/publish.ts`): `show`, `uploaded --id`, `approve --by`, `thumbnail <file>`, `scheduled --at`, `published`, `updated --fields`, `failed --step --error`, `unpublished`, `retracted`, `add <output-id> --kind`. Every verb is idempotent (an existing key prints the event, exit 0) and refuses with exit 2 without writing. The API verbs (`src/lib/uploader.ts` over `src/lib/youtube.ts`, plain `fetch`, no googleapis) write the same events: `auth` (one-time consent), `upload` (always private, with thumbnail and captions, resumable through `video/upload-session.json`), `push` (changed metadata), `go-live [--at]` (public or scheduled; needs the ledger's `approved`), `sync` (read back). The hand verbs remain the fallback.
- `npm run brand` writes every brand kit into `brand/<brand>/` (SVGs committed, PNG/JPG rasters gitignored) and the site's seals `public/commissions/<key>.png`, from `scripts/brand/draw.js`, each `kit.json` and `src/config/site.ts`, fitting text in the brand fonts in Remotion's headless Chrome. Re-run after changing a drawing or a kit; it also writes the site's share cards (`public/og/`, one per public story in `public/og/stories/`, so re-run it when a story's question changes), seals (`public/commissions/`), stamps in both inks (`public/stamps/`, shown by `src/components/Stamp.astro`), favicon set and header logo.
- `npm run music -- cues <topic> <story-id> [--composition <id>] [--force]` drafts `video/music.json` from the script's sections over a cleared composition.
- `npm run music -- import|render|show <composition>` keeps `music/<composition>/` (compositions rendered by strudel-bench; `music/README.md` is the contract, `scripts/briefs/strudel-bench.md` the handoff to that repo).
- `npm run shorts -- discover <topic> <story-id>` writes `topics/<topic>/scripts/<slug>/shorts.json`: one Short candidate per storyboard scene of a produced video whose sentences are verified and approved and that asserts a fact, merged with the reviewer's `shorts-review.json` (`scripts/briefs/shorts.md`: keep, slug, format, hook, how each qualification is carried). `show <topic> <story-id> [key]` prints a candidate with its passages. A ready candidate is produced as `<story-id>/shorts/<slug>` through the same CLIs as a video (`script`, `video`, `board next`, `/produce`, `publish`).

## Rules

- A public URL never disappears: `public-urls.json` lists them (`npm run links -- freeze`), and a story whose id changes gets a `topics/<topic>/moved.json` entry (old story id to new, written by a person; Astro's `redirects` turns it into a noindex redirect page) or the build test fails. Every link to a page of the site is built from a node id of the content graph (`urlOf` in `src/lib/content-graph.ts`, derived every build, never stored), never from a title.
- Calls to action: `topics/<topic>/scripts/<slug>/cta.json` is an agent's choice from `scripts/briefs/cta.md` (`npm run links -- cta <topic> <story-id>` shows the destinations and checks the file), checked by `src/lib/cta.ts` against the content graph: a destination whose value check fails is dropped, never shown, and the default is the matter page. A script, storyboard or render never carries one; the description's Links block and the matter page do. A `commercial` destination needs a disclosure and a person's `approvedBy` (never `automated:`) and is never primary over a tool or the evidence.
- `public-record.json` is written only by `npm run report` and `npm run article -- correct` (`src/lib/public-record.ts`); every revision needs a note (`npm run report -- note`), the build test refuses one without.
- Never hand-edit `topics/<topic>/store/` (`topics.json`, `videos/*.json`). Go through `npm run record`, `record-sources`, or the CLI. The agent batch formats (`h*.json`, `sv_*.json`) are typed and checked in `src/lib/batches.ts`; change the type, the check and the brief together.
- Evidence belongs to the claim, not the source. A verdict on a claim counts for every source that makes it. Adding a source never needs re-judging old claims.
- An AI guess counts for at most 0.5 confidence; a study verdict overrides it only when at least as confident.
- Canonical claim text: one line, mechanism-level, no numbers that belong to one source. No personal data in notes or claims; the store is public.
- `.claude/skills/watcher/SKILL.md` is a verbatim copy of `../retire-sim/watcher/SKILL.md`. Change it upstream and re-copy; don't edit it here.
- `stories.json` is derived: never hand-edit it, and never store passage text in it (references only; `show` re-reads passages). The validator in `src/lib/evidence.ts` must stay deterministic and fail closed; an AI guess never counts as verification; contextual evidence never decides. Semantic judgment lives only in `story-review.json`, keyed by stable ids, so runs stay reproducible. A story with more than one claim is never `ready` without a review. A video may answer a chain of up to three questions (`chain` on the first story's review): each chained story keeps its own claims and audit, the video is ready only when every one is, chains do not nest, a chained story is `partOf` the first and the board never starts it, `chainCandidates` are suggestions only, a chained video carries at most `MAX_CHAIN_CLAIMS` (14), the list cap counts videos (a follow-up takes no slot), and a chained package carries each question's premise, tension, whyWatch and arc plus `chainWhy` (a one-question package has no `questions`). A story-review.json entry must name a current candidate (`staleReviewIds`, tested). Stories have no length format: a script is as long as its questions need.
- Article artifacts: the agent writes `article.json` and `article-review.json` (different agents); `article-validation.json`, `article.md` and `article-release.json` are derived; the site renders only the release snapshot.
- Script artifacts: the agent writes `script.json`, `script-review.json` and `storyboard.json`; everything else in `topics/<topic>/scripts/<slug>/` is derived by the script-stage modules (`src/lib/evidence-package.ts`, `script-validation.ts`, `script-md.ts`, `release.ts`, with the shared types in `script.ts`) and `src/lib/storyboard.ts`, and is never hand-edited. The writer and the reviewer are different agents. A factual sentence needs an assertion per claim it makes; figures, quotations and calculations must trace to a cited passage; approvals are by fingerprint, so a changed sentence is re-reviewed. The storyboard never carries narration of its own; its chart data is numeric points with a unit and a cite (never prose values), its required assets are registered by id, and its timing is per sentence. Add passages to the corpus only through `record-sources` (a verdict on a claim), never by citing uncited lines. A script has no word target and says each thing once: sections `hook`, `setup`, `investigation`, `answer`, `takeaway` (`SECTIONS`), or `hook`, `question-N`, `close` for a chain. Pacing (`pacing()` in `script-validation.ts`: `slow-start`, `number-dense`, `repetition`) warns on every script; a reviewer retires one only with a disposition.
- Video: `src/video/kinds.ts` is the closed map from storyboard scene to renderer, one `KindSpec` record per kind (component, accepted categories, inference, required cues, flags). Generic kinds there are inferred from category, chart type and assets; bespoke kinds are registered per video in `src/video/bespoke/` (keyed `<topic>/<story slug>`, names unique across videos), named per scene in that video's `render.json` and checked against the category. An unsupported scene fails the build, never a placeholder. `src/video/remotion/**`, `src/video/bespoke/**` and `types.ts`, `kinds.ts`, `words.ts`, `chart.ts`, `cues.ts`, `excerpt.ts` are browser-safe (no node imports). Cues name narration words in `render.json`; the timeline fails if the word is not spoken. Chart components read `chart.points`, text comes from `onScreenText`, excerpts from the cited passage; `options` carry layout choices only, never figures. What a scene draws must fit: `SceneView` in `Video.tsx` checks every rendered frame and fails the render when visible text leaves the frame or runs into the citation (lay out against `citationTop` from `Citation.tsx`, never a fixed row height times an unbounded count). The look lives in `remotion/theme.ts`: one palette (saturated colour, drifting backdrop, a camera that pushes and punches on cues), rendered into the one `segment.mp4` that QA, the board and the review package use. Components read `theme` at render time, never into a module-level constant, and draw one look: there is no brand switch. Brand marks in a video come from the kit: a render stages the story's institution's kit into `video/brand/` (`src/video/brand.ts`), so a scene uses `staticFile('brand/<slot>.png')`, never a mark drawn ad hoc. A landscape video of a published topic ends on an unnarrated scene `end` (kind `close-card`) the timeline appends after the last storyboard scene: the kit's close card, then its end screen for YouTube's end-screen elements; a storyboard plans no scene for it. A new component file goes in `COMPONENTS` (`remotion/scenes/index.ts`, keyed by its file name) so a kind can name it and the render cache sees its edits. Editing `Video.tsx` or another shared Remotion file invalidates every cached chunk.
- Soundtrack: `music/<composition>/composition.json` is written by `npm run music -- import`, never by hand except `licence.cleared`, `intensity` and `loop`, which it preserves; the WAVs are never committed. `video/music.json` holds cues over scene anchors, never seconds and never a composition; `video/mix.json` and `video/review/` are derived. Mixing is PCM in `src/video/mix.ts` (Remotion's ffmpeg has no afade, aloop or limiter), driven by `src/video/assemble.ts` (chunks, narration track, soundtrack, mux); `src/video/music.ts` is the contract only; the music is turned down to keep the peak under the ceiling, the narration never. The chunk cache key must stay ignorant of music, and only a full render mixes (a scene or range render is narration only). `mix.json` levels are as mixed, after the ceiling's scaling. A re-import keeps `cleared` only while the sound sources are unchanged. The review package refuses an mp4 whose sha is not the one the build report's QA checked. Narration licence and music clearance are recorded separately (one `clearance` in the build report, nowhere else) and a passing build never marks either cleared.
- Production: the board binds a build to the script, storyboard and `video/render.json` (a changed render.json asks for a new render). The board (`src/lib/production.ts`) is the state machine; every halt has a `kind` and the next step names a command or a brief, so `/produce` never parses prose. The `graphics` stage sits between `storyboard` and `lock`. An automated lock is approved by `automated: /produce run started by <name>`. A writer pass has three revisions to clear its blocking findings (the run sets `passStartRevision` for a send-back pass; a `generation.corrective` entry a person authorised is the only way past the limit; a revision that only answers warnings is not limited, and the board routes those back to the writer as `review-findings`); a writer that needs a passage sets `generation.needsEvidence` and stops. `record-sources` refuses any new verdict on a claim and document a script cites (the store keeps one per pair) unless `--replace-cited`; `/produce` never passes it.
- Publishing: `publish.json` is the one record of what publishing adds (uploads, approvals, schedules, publications, failures, a person's tags, title or thumbnail), per output, append-only. Its `events` are written only by `npm run publish`; `metadata` may be hand-edited and is validated at build. A build is its mp4 sha (from `review.json`), the upload metadata its composed sha, so a thumbnail or title change is an `updated` event, never a re-render. Titles, chapters and descriptions stay derived in `video/review/`; the ledger holds overrides only. A public upload needs a prior `approved` for that build. An approval binds the build and the composed title (a changed title asks again); the latest decision on a build decides it, and `changes-requested` (notes, each optionally placed `[m:ss sc20 s31]`) sends it back: the board's column `changes-requested`, its send-back prompt carrying the notes. Only a person approves or goes live (`automated:` is refused for both), approval needs every checklist item ticked, and a Short is made and approved before its video launches and goes live with it, right after the output it derives from (go-live refuses it before). A live video is never replaced (a re-release is a new output via `add`), and the board stops `/produce` on it. `production.json` holds `queued` and `parked` only. The publish module never imports the store, corpus or evidence gate. YouTube credentials live outside git: `.env` names the Desktop OAuth client JSON (`YOUTUBE_OAUTH_CREDENTIALS_PATH`, e.g. `./.secrets/youtube-oauth.json`, gitignored) and `auth` stores the refresh token in that file (or `YOUTUBE_CLIENT_ID`, `YOUTUBE_CLIENT_SECRET`, `YOUTUBE_REFRESH_TOKEN` directly in `.env`), never in the repo or an event; `upload` never sends anything but `private`, and a lost upload session stops and asks a person rather than uploading twice. Captions (`captions.en.srt`) and the YouTube-sized description are written by `npm run video -- package`; the full source list stays on the topic page.
- The working pages (production board, story ideas, scripts, the review page, admin index) live in `src/admin/` and are routed only by the dev server (`astro.config.mjs` injects them when `command === 'dev'`); a build never emits them and links to them are guarded by `import.meta.env.DEV`. Only topics an institution claims (`commissions` in `src/config/site.ts`, `publicTopicNames()`) are built; the brand charter is `brand/`. The production board (`src/admin/production.astro`) shows one row per video in a sortable, filterable table, its state who acts next (`COLUMNS`, `columnOf` in `production.ts`; a follow-up has no row). Red in a row means only that `/produce` stopped (`revision-limit`, `story-left` or a `stop:` step); every other halt is its next step. The review page (`src/admin/review.astro`, `/<topic>/review/<folder>`, model in `src/lib/review-view.ts`) is rendered per request; its media (`media.ts`) streams the packaged build from disk and its actions (`review-action.ts`) refuse any other origin and any build but the current one, writing through the publish verbs or running the CLI as a job (`src/lib/review-job.ts`, `video/review-job.*`, gitignored).
- Shorts: a Short is a nested production, id `<story-id>/shorts/<slug>`, folder `scripts/<story slug>/shorts/<slug>/` (`shortOf`, `scriptDir` in `src/lib/script.ts`), never a story. `shorts.json` is derived (never hand-edited, byte-identical on a rerun); the judgment lives in `shorts-review.json`, keyed by candidate key (the scene's first sentence id); no candidate is ready without it, at most `MAX_SHORTS` (3) per video, and the parent must be locked. Its evidence package is a filter of the parent's (`buildShortPackage` in `src/lib/shorts.ts`) with a `short` block, never built from the store or the story; a Short never touches the store, the corpus, a verdict or `record-sources`. The block selects `SHORT_SECTIONS` (`hook`, `finding`, `close`), makes `scope` (a claim outside the package), an unplaced `needs-qualification` and a figure in `close` blocking, and caps the storyboard at `SHORT_MAX_SECONDS` (60; QA fails a measured Short over 180). The frame is `PORTRAIT` (1080x1920) laid out by `SHORT_LAYOUT` (`src/video/types.ts`): the badge and format eyebrow above `top`, the content band, the caption band, the citation block ending above YouTube's overlay; a Short draws only with `SHORT_GENERIC` (`kinds.ts`, names `short-*`, chosen by `registryFor(pkg)`), in the Commonwealth look (`brand` in `theme.ts`, faces embedded by `fonts.ts`, the badge, captions and backdrop in `remotion/Portrait.tsx`); the landscape videos keep `theme` until they are rebranded. A packaged Short records itself as the output `short:<slug>` in its parent's `publish.json` (`derivedFrom: youtube`, `source` its folder; `npm run publish` maps a short id to that entry); the related-video link has no API and is a Studio step the ledger records as `updated --fields relatedVideo`. A Short's board row sits under its parent's and is never the topic's next step.
- The workflow diagram on `/admin` (`flow` in `src/admin/index.astro`: who acts, what runs between) is the map a person follows. A change that adds, removes or reorders a stage, a human step or a halt a person resolves updates `flow` in the same commit; `planned` marks a step not built yet.
- Calculators (`src/tools/`, `toolOf`): a tool's defaults cite a dataset or a passage; `src/tools/**` holds no outbound link and no partner.
- Site navigation is a tree (Record, institution, inquiry, matter, with the data page beside its inquiry): every page below home has the `ReportHeader` trail to each level above (a phone shows only the parent), and lists everything below it. Every list of matters is `MatterList.astro` in `matterOrder` (`content-graph.ts`: a live video first). A link list that mixes kinds of destination (a matter, a video, an article, data, a tool, an inquiry, an outside page) marks each with `KindIcon.astro` from the `SourceIcons` sprite, its kind also said in text or an accessible label. The dist test walks the site from `/`: every page reachable, every matter within three clicks.
- Site pages are rendered at build time. Keep client JS to the tab bar, claim search, the matter page's video facade, the board's Copy buttons and its table sort and filter, and the review page's seek links, note stamp, remembered name and job refresh, plus the calculators in `src/tools/`.
- Web quality: a change to a public page, component, layout, style or `public/` follows `.claude/skills/web-quality/SKILL.md` and ends with `npm run quality` (`RESULT: PASSED`). The gate is `tests/web-quality.test.ts` (html-validate, page-weight budgets, headers, third-party allowlist; in `npm test`) and `tests/browser/site.test.ts` (reflow 320-1440, keyboard, axe WCAG 2.2 A/AA, lab CLS, reduced motion; Chromium locally, three engines in CI). Its limits and exceptions live in `tests/web-quality.json`: an exception names one rule, a narrow page (and selector) pattern and a reason, a stale one fails, and a change never adds one for a finding it caused. Passing it is never reported as WCAG conformance or field Core Web Vitals.
- Find the repo root through `ROOT` in `src/lib/io.ts` (or a `root` argument defaulting to it), never `process.cwd()` or `import.meta.url`. File helpers (`sha`, `readJson`, `toJson`, ...) live there too; no stage imports another stage's module for a utility.
- The evidence gate and the script stage judge a `Corpus` (`src/lib/corpus.ts`), built from a `Topic` only by `corpusOf`; they never import `topics.ts`. The library layer never imports from `src/video/` (the board reads the build report through `BuildSummary` in `src/lib/build-report.ts`).
- Names: `video-knowledge` is the repo and the production tooling; the public site is **Commonwealth of Reason** (commonwealthofreason.com, Cloudflare via `wrangler.jsonc`; `DEPLOY_TARGET=pages` builds the GitHub Pages mirror under `/video-knowledge/`); its YouTube channels are commissions (`commissions` in `src/config/site.ts`: name, full name, handle, the topics they publish). Videos are branded with the full commission name or the handle, never with the repo name. The fiction never touches the evidence: `site.disclosure` ("The Commonwealth is fictional. The research is real.") appears once per surface (the site footer, a video description), the copy otherwise stays in character without explaining the conceit, and no in-world mark (APPROVED, a finding stamp) may claim more than the verdicts do. Only channels a person has created go in `commissions`; never invent a handle. Site name, nav, author links and commissions live in `src/config/site.ts`. Brand assets: `brand/slots.json` lists every asset slot; `brand/<brand>/kit.json` (`cor` for the Commonwealth, else the commission key) holds the brand's palette, emblem and slogan and maps each slot to the SVG `npm run brand` drew, and `accounts.json` beside it records what each live account (YouTube, X, ...) shows, avatar and banner by slot id. Every brand uses the same designs (`scripts/brand/draw.js`); never hand-edit a kit SVG, and a new page or graphic takes its colours and marks from the kit, never from memory. `tests/accounts.test.ts` checks both. Build internal links with `href()` from `src/lib/url.ts` so they respect Astro's `base`.
