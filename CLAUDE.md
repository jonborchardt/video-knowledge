# video-knowledge

Topic knowledge stores (claims from YouTube videos and blog posts, judged against studies) published as an Astro site. The runbook is `docs/OPERATIONS.md`, the command reference `docs/COMMANDS.md`, the modules `src/modules/README.md`, the orchestration `src/orchestration/README.md`. Each topic lives in `topics/<topic>/` (`topicDir()` in `src/shared/io.ts`); a cite (`<topic>/sources/<file>.txt#L10-L24`) is relative to `topics/`, so the cite text in the store, reports and approved scripts never carries the folder. The workflow for adding a topic is in README.md; the agent contract for the watcher CLI is `.claude/skills/watcher/SKILL.md`; the briefs handed to parallel agents are in a module's `briefs/` folder, `src/modules/<module>/briefs/`.

## Commands

One line per command; the full descriptions are in [docs/COMMANDS.md](docs/COMMANDS.md), the runbook by situation in [docs/OPERATIONS.md](docs/OPERATIONS.md). Verification is change-driven (Jon, 2026-11-01): focused tests and `npm run check` per task; `npm run validate`, the boundary test and the e2e rehearsal (`node docs/superpowers/plans/e2e.cjs rehearse`, when the plan files are present) once on the final candidate of a phase or branch, never again after a fast-forward merge; `/produce` and the runner still validate before an automated commit.

- `npm run check` (incremental `tsc --noEmit` + cached lint), `npm run validate` (typecheck, lint, format check, build, tests: what CI runs), `npm run quality [-- --audit]` (the web-quality gate for site changes; `RESULT: PASSED`), `npm run test:browser` (the browser project: the site suite and the admin live test), `npm run format`, `npm run rehearse -- <topic> <story-id>` (a go-live in a throwaway copy).
- `npm run report [-- <topic> | seed [topic] | note <topic> <claim> "<note>"]` regenerates `report.json` and keeps `public-record.json` (needs the watcher checkout; commit the result).
- `npm run watcher`, `record`, `record-sources`, `merge-claims` are the store's writers (never hand-edit `topics/<topic>/store/`); `npm run evidence -- search|fetch-doc|lists|groups|check-batch|check-verdicts|dedupe|check-merges|collide|thin|scanned` are the deterministic research verbs (`search` and `fetch-doc` the only two a collect agent may run).
- `npm run topics -- validate|show|context|approve|reject|park|batch|sent|claim` keeps `proposals/<slug>.json`; only a person approves or rejects.
- `npm run stories -- discover|show|validate <topic>` writes `stories.json` (derived) and runs the evidence gate.
- `npm run script -- package|validate|show|storyboard|lock|run|send-back <topic> <story-id>` is the script stage; `npm run article -- validate|show|lock|correct|reaffirm|request-correction|decide|sent <topic> <story-id>` the companion article; refusals exit 2 and write nothing.
- `npm run video -- init|check|frames|narrate|timeline|render|qa|spike|package|final|preview <topic> <story-id>` is the media (`final --approved-by` is the release build in the Azure voice); `npm run music -- cues|import|render|show`; `npm run shorts -- discover|show <topic> <story-id>`; `npm run brand` writes every brand kit and the site's seals, cards and stamps; `npm run packaging -- package|manifest`.
- `npm run board -- next <topic> <story-id> [--json]` is the board's answer for one story, `npm run board -- topic <topic>` the research board's; `/produce` (`.claude/skills/produce/SKILL.md`) loops on it in a session.
- `npm run run -- story <topic> <story-id> [--approver] [--until <stage>] [--model <alias>] [--notes-file] [--fresh] [--no-commit]` is that loop as code; `topic <topic>` the research pipeline; `maintain <topic>` the scan and the article pass; `discover`; `launch <topic> <story-id>`; `probe <topic> <story-id>` (the tick's deploy step for one launch) and `settle <topic> <story-id>` (clears an `awaiting-person` halt a publication made moot), both by hand; `clear <topic> <story-id> --by`; `status [--json]`; `tick` (the control plane), `work [--job] [--dry-run]` (the work plane), `pick [--dry-run]`, `schedule --print`; `verified <integration> --by "<name>" --evidence <ref>` records a person's verification in `readiness.json` (its only writer; evidence checked, no flag changed).
- `npm run mail -- ask|questions|report|test|init|send|fetch` is the conversation with the approver by email (`ask` blocks until the reply: run it in the background); see Rules.
- `npm run publish -- <verb> <topic> <story-id> [--output <id>]` keeps the publishing ledger (`show`, the hand verbs, `accept-draft`, `request`, `message-sent`, `decide`; the API verbs `auth|upload|push|go-live|sync|verify`); `npm run social -- show|compose|post` posts on X by policy; `npm run links -- freeze|check|live|cta|cta approve`.

## Rules

- A public URL never disappears: `public-urls.json` lists them (`npm run links -- freeze`), and a story whose id changes gets a `topics/<topic>/moved.json` entry (old story id to new, written by a person; Astro's `redirects` turns it into a noindex redirect page) or the build test fails. Every link to a page of the site is built from a node id of the content graph (`urlOf` in `src/modules/website/content-graph.ts`, derived every build, never stored), never from a title.
- Calls to action: `topics/<topic>/scripts/<slug>/cta.json` is an agent's choice from `src/modules/website/briefs/cta.md` (`npm run links -- cta <topic> <story-id>` shows the destinations and checks the file), checked by `src/modules/website/cta.ts` against the content graph: a destination whose value check fails is dropped, never shown, and the default is the matter page. A script, storyboard or render never carries one; the description's Links block and the matter page do. A `commercial` destination needs a disclosure and a person's `approvedBy` (never `automated:`) and is never primary over a tool or the evidence.
- `public-record.json` is written only by `npm run report` and `npm run article -- correct` (`src/shared/public-record.ts`); every revision needs a note (`npm run report -- note`), the build test refuses one without.
- Never hand-edit `topics/<topic>/store/` (`topics.json`, `videos/*.json`). Go through `npm run record`, `record-sources`, or the CLI. The agent batch formats (`h*.json`, `sv_*.json`) are typed and checked in `src/modules/evidence/batches.ts`; change the type, the check and the brief together. `topics/<topic>/applicability.json` (each study verdict's `direct`/`partial`/`contextual`, keyed `<claim>|<cite>`) is written only by `record-sources` from the `sv_` field `applicability`; the gate treats it as a ceiling that `story-review.json` may narrow, never widen; a verdict without one keeps the wording heuristic.
- Evidence belongs to the claim, not the source. A verdict on a claim counts for every source that makes it. Adding a source never needs re-judging old claims.
- An AI guess counts for at most 0.5 confidence; a study verdict overrides it only when at least as confident.
- Canonical claim text: one line, mechanism-level, no numbers that belong to one source. No personal data in notes or claims; the store is public.
- `.claude/skills/watcher/SKILL.md` is a verbatim copy of `../retire-sim/watcher/SKILL.md`. Change it upstream and re-copy; don't edit it here.
- `stories.json` is derived: never hand-edit it, and never store passage text in it (references only; `show` re-reads passages). The validator in `src/shared/evidence-gate.ts` must stay deterministic and fail closed; an AI guess never counts as verification; contextual evidence never decides. Semantic judgment lives only in `story-review.json`, keyed by stable ids, so runs stay reproducible. A story with more than one claim is never `ready` without a review. A video may answer a chain of up to three questions (`chain` on the first story's review): each chained story keeps its own claims and audit, the video is ready only when every one is, chains do not nest, a chained story is `partOf` the first and the board never starts it, `chainCandidates` are suggestions only, a chained video carries at most `MAX_CHAIN_CLAIMS` (14), the list cap counts videos (a follow-up takes no slot), and a chained package carries each question's premise, tension, whyWatch and arc plus `chainWhy` (a one-question package has no `questions`). A story-review.json entry must name a current candidate (`staleReviewIds`, tested). Stories have no length format: a script is as long as its questions need, or as long as the review's `targetDurationSeconds` says.
- Article artifacts: the agent writes `article.json` and `article-review.json` (different agents); `article-validation.json`, `article.md` and `article-release.json` are derived; the site renders only the release snapshot.
- Script artifacts: the agent writes `script.json`, `script-review.json` and `storyboard.json`; everything else in `topics/<topic>/scripts/<slug>/` is derived by the script-stage modules (`src/modules/script/`: `evidence-package.ts`, `script-md.ts`, `cli.ts`; the lock's checks in `src/shared/release-check.ts`, with the shared types in `src/shared/types.ts`, the text helpers in `src/shared/sentences.ts` and the checks in `src/shared/sentence-validation.ts`) and `src/modules/storyboard/storyboard.ts` (the storyboard builder; `src/lib/storyboard.ts` is only the type re-export the hashed video files import), and is never hand-edited. The writer and the reviewer are different agents. A factual sentence needs an assertion per claim it makes; figures, quotations and calculations must trace to a cited passage; approvals are by fingerprint, so a changed sentence is re-reviewed. The storyboard never carries narration of its own; its chart data is numeric points with a unit and a cite (never prose values), its required assets are registered by id, and its timing is per sentence. Add passages to the corpus only through `record-sources` (a verdict on a claim), never by citing uncited lines. A script says each thing once: sections `hook`, `setup`, `investigation`, `answer`, `takeaway` (`SECTIONS`), or `hook`, `question-N`, `close` for a chain. A story's optional `targetDurationSeconds` (`story-review.json`, copied onto the story, the package, the script and the storyboard, read by QA from the timeline) is the authoritative duration constraint (`src/shared/duration.ts`): the band it falls in (micro up to 20 s, short up to 90 s, standard up to 8 min, long) supplies editorial defaults, never a format and never a validation exception: the words budget (within 35%), the plain form's sections, the sentence and scene counts, which pacing checks run, the article's paragraphs and tables, the Shorts' count and target; the measured runtime must land within the larger of 35% and 3 s of the target (QA `runtime`, blocking; a micro or short story is measured by its speech, a longer one by its frame span less the end card). A story without a target keeps today's rules, a shorter story is as valid as a longer one, and evidence, provenance, fingerprints, QA and publishing never move with the target. Pacing (`pacing()` in `src/shared/sentence-validation.ts`: `slow-start`, `number-dense`, `repetition`) warns on every script; a reviewer retires one only with a disposition.
- Video: `src/modules/video/kinds.ts` is the closed map from storyboard scene to renderer, one `KindSpec` record per kind (component, accepted categories, inference, required cues, flags). Generic kinds there are inferred from category, chart type and assets; bespoke kinds are registered per video in `src/modules/video/bespoke/` (keyed `<topic>/<story slug>`, names unique across videos), named per scene in that video's `render.json` and checked against the category. An unsupported scene fails the build, never a placeholder. `src/modules/video/remotion/**`, `src/modules/video/bespoke/**` and `types.ts`, `kinds.ts`, `words.ts`, `chart.ts`, `cues.ts`, `excerpt.ts` are browser-safe (no node imports). Cues name narration words in `render.json`; the timeline fails if the word is not spoken. Chart components read `chart.points`, text comes from `onScreenText`, excerpts from the cited passage; `options` carry layout choices only, never figures. What a scene draws must fit: `SceneView` in `Video.tsx` checks every rendered frame and fails the render when visible text leaves the frame or runs into the citation (lay out against `citationTop` from `Citation.tsx`, never a fixed row height times an unbounded count). The look lives in `remotion/theme.ts`: every video, landscape or Short, draws from the owning institution's kit through `theme` (`themeOf` fills its roles from the timeline's `palette`, `Video` calls `setTheme` before any scene renders: the kit's ground, its accent lifted to glow, the Commonwealth faces, semantic data colours), with a drifting backdrop and a camera that pushes and punches on cues, rendered into the one `segment.mp4` that QA, the board and the review package use. Components read `theme` at render time, never into a module-level constant, and hold no literal colour (`theme.ts` is the only home of one; a tint is `alpha(theme.<role>, a)`): there is no brand switch. Brand marks in a video come from the kit: a render stages the story's institution's kit into `video/brand/` (`src/modules/video/brand.ts`), so a scene uses `staticFile('brand/<slot>.png')`, never a mark drawn ad hoc. A landscape video of a published topic ends on an unnarrated scene `end` (kind `close-card`) the timeline appends after the last storyboard scene: the kit's close card, then its end screen for YouTube's end-screen elements; a storyboard plans no scene for it. A new component file goes in `COMPONENTS` (`remotion/scenes/index.ts`, keyed by its file name) so a kind can name it and the render cache sees its edits. Editing `Video.tsx` or another shared Remotion file invalidates every cached chunk. `componentVersion` (`src/modules/video/render.ts`, the chunk cache key and each bespoke graphic's approval key) hashes normalised sources (type-only imports removed, runtime imports followed: static, side-effect, re-exports, dynamic and require, read from the TypeScript AST), so a move of the tree or of a type's home never moves a key; the one-time migration to it is recorded in `video/key-migration.json` beside each visual review (the verb that wrote it is gone).
- Soundtrack: `music/<composition>/composition.json` is written by `npm run music -- import`, never by hand except `licence.cleared`, `intensity` and `loop`, which it preserves; the WAVs are never committed. `video/music.json` holds cues over scene anchors, never seconds and never a composition; `video/mix.json` and `video/review/` are derived. Mixing is PCM in `src/modules/video/mix.ts` (Remotion's ffmpeg has no afade, aloop or limiter), driven by `src/modules/video/assemble.ts` (chunks, narration track, soundtrack, mux); `src/modules/video/music.ts` is the contract only; the music is turned down to keep the peak under the ceiling, the narration never. The chunk cache key must stay ignorant of music, and only a full render mixes (a scene or range render is narration only). `mix.json` levels are as mixed, after the ceiling's scaling. A re-import keeps `cleared` only while the sound sources are unchanged. The review package refuses an mp4 whose sha is not the one the build report's QA checked. Narration licence and music clearance are recorded separately (one `clearance` in the build report, nowhere else) and a passing build never marks either cleared.
- Production: the board binds a build to the script, storyboard and `video/render.json` (a changed render.json asks for a new render); a packaged build whose recorded look (`lookFingerprint` in `src/shared/look.ts`: the kit palette, the kit cards scenes draw, `theme.ts`) is not the current one halts `look-stale` and names `npm run video -- final`, and is never approved (`recordApproved`, the review page); `boardNext` stays done, so `/produce` never re-renders it, and a live or scheduled video never halts on it. The board (`src/orchestration/production.ts`) is the state machine; every halt has a `kind` and the next step names a command or a brief, so `/produce` never parses prose. The `graphics` stage sits between `storyboard` and `lock`, the `article` stage (written, reviewed and locked: `article-release.json`) between `scored` and `packaged`; the board gives it its own column (`article`, between `producing` and `draft-review`); once released, a correction or a stale finding is listed under Article corrections, never a stage. An automated lock is approved by `automated: /produce run started by <name>`. A writer pass has three revisions to clear its blocking findings (the run sets `passStartRevision` for a send-back pass; a `generation.corrective` entry a person authorised is the only way past the limit; a revision that only answers warnings is not limited, and the board routes those back to the writer as `review-findings`); a writer that needs a passage sets `generation.needsEvidence` and stops. `record-sources` refuses any new verdict on a claim and document a script cites (the store keeps one per pair) unless `--replace-cited`; `/produce` never passes it.
- Module API: a module exposes pure `validate(...)` over parsed artifacts and, where the board asks, `inspect(topic, story)` returning `Inspection` (`src/shared/inspect.ts`: `missing | invalid | stale | ready`, findings, output) with no workflow vocabulary. Only the board (`production.ts`) maps an inspection to a `HaltKind` and a next command; a module never answers what runs next or whether something may go live. Publishing's `OutputStep` (`outputState(...).step`: `verb`, `actor`, `args`, `retryable`) is the one exception that names a verb: it is the ledger's own account of what the output needs, with an actor; the board renders it (`renderStep`) and the runner decides when to run it.
- Architecture principles (Milestone 1 drew them; every later milestone keeps them). A capability is a module (`src/modules/<cap>/`: `index.ts`, `cli.ts`, `briefs/`, `tests/`, `README.md`, listed in `src/modules/README.md`); a new capability is a new module, never a folder inside another module or a home in `src/shared/`. Topic discovery (proposals) is separate from evidence (research; the store's only writer); publishing (YouTube) from social (X); article (editorial text and its corrections) from website (rendering, build, deploy); institution, topic and story stay distinct things. Orchestration (`src/orchestration/`) owns coordination only: derived state, routing, and, from Milestone 2, scheduling, execution, retries, budgets and notifications; it never judges content and never writes a module's artifact (a write is the owning module's CLI as a child process). State is files in the repo, derived at read; a decision carries who, when and the sha of what it binds; there is no database, queue, event bus, distributed orchestrator, stored workflow state machine, generic agent framework or generic publishing framework. Agents (a session's or `claude -p`) write artifacts a deterministic validator checks (scripts, reviews, batches, proposals, and components only where the graphics brief says); they never write machinery (code outside those paths, configuration, settings, `package.json`), never publish, post, push or hold a secret, and a writer and its reviewer are different agents. A person's authority is code, not policy: release approval, scheduling, go-live, paid links, topic approval, unpublishing and retraction are a person's acts; only draft review is configurable. Every automated step is a CLI verb a person can run by hand, so the manual workflow stays documented and rehearsed (`npm run rehearse`, the e2e rehearsal).
- Publishing: `publish.json` is the one record of what publishing adds (uploads, approvals, schedules, publications, failures, a person's tags, title or thumbnail), per output, append-only. Its `events` are written only by `npm run publish`; `metadata` may be hand-edited and is validated at build. A build is its mp4 sha (from `review.json`), the upload metadata its composed sha, so a thumbnail or title change is an `updated` event, never a re-render. Titles, chapters and descriptions stay derived in `video/review/`; the ledger holds overrides only. A public upload needs a prior `approved` for that build. An approval binds the build and the composed title (a changed title asks again); the latest decision on a build decides it, and `changes-requested` (notes, each optionally placed `[m:ss sc20 s31]`) sends it back: the board's column `changes-requested`, its send-back prompt carrying the notes. Only a person approves or goes live (`automated:` is refused for both), approval needs every checklist item ticked, and a Short is made and approved before its video launches and goes live with it, right after the output it derives from (go-live refuses it before). Milestone 2: `outputState(...).step` is the structured next step (`OutputStep`: `verb`, `actor` person/automation/youtube/none, `retryable`, `failed`), rendered by `renderStep`; the release loop (`src/orchestration/run/release.ts`, inside `npm run run -- story` after `packaged`) dispatches on it and writes only through the CLIs. `review.draft` in `automation.json` is the one configurable review: `person` and `shadow` upload the draft and wait for the person (`shadow` also records a draft-review agent's verdict in `.automation/shadow.json`, with no effect); `agent` lets the draft-review agent accept (`accept-draft` with `automated: draft-review by <model> session <id>`) or send back a draft build, never a release. `request --channel email` writes `approval-requested` binding `video/review/release-manifest.json`'s `releaseSha` (packaging writes the manifest for a release build; `packaging -- manifest` rewrites it; a re-packaged output, a re-locked article or a changed call to action moves the sha and voids the request; `PAID OK` does not), signed with `APPROVAL_SECRET` from `.env`; `openRequest` reads it; `message-sent` records the mail. A decision's `via` says how it arrived (the review page passes `--via review-page`, the inbox adapter `email:<message id>`, the tick `tick:<request id>`). Phase 3: `decide --request <id> --by <name> --verdict ok|schedule|changes [--at <ISO>] [--note ... [--at-seconds n] [--scene id] [--sentence id]]* [--paid <cta id>]* --via <channel:id>` (`src/modules/publishing/decide.ts`) applies a person's decision against the exact manifest the request bound (a moved `releaseSha`, an expired or decided request, an automated name, a schedule under `approvals.scheduleLeadMinutes`, a paid id outside the manifest are refused), every step idempotent and `decided` last: each paid link through `links -- cta approve` and `video package` as children, one `approved` per output (`via.checklist: asserted-by-email`), `push` when behind, `sync`, then the video's `go-live` now or at the time; the Shorts are approved with it and go live from the tick's due step after the video, in order; `go-live`, `scheduled` and `published` carry `via`. A fixture topic's output goes `unlisted` at most on that decision, never public (`sync` and `verify` read unlisted as its published state; the `published` event records the visibility). Channel credentials are per commission (D18): `YOUTUBE_OAUTH_CREDENTIALS_PATH_<KEY>` names a commission's own OAuth client file, every verb resolves the commission from the topic, `auth [--commission <key>]` stores the refresh token there, and a commission without one keeps the shared default; `upload` refuses before any byte unless the authenticated account's channel is the commission's `YOUTUBE_CHANNEL_ID_<KEY>` (or `YOUTUBE_CHANNEL_ID`) in `.env`. A live video is never replaced (a re-release is a new output via `add`), and the board stops `/produce` on it; after go-live, `npm run publish -- verify`, then `npm run report -- seed <topic>`, `npm run brand` (a story's share card exists only once it is live), `npm run build`, `npm run links -- freeze` and a commit bring the story to the site. `production.json` holds `queued` and `parked` only. The publish module never imports the store, corpus or evidence gate. YouTube credentials live outside git: `.env` names the Desktop OAuth client JSON (`YOUTUBE_OAUTH_CREDENTIALS_PATH`, e.g. `./.secrets/youtube-oauth.json`, gitignored) and `auth` stores the refresh token in that file (or `YOUTUBE_CLIENT_ID`, `YOUTUBE_CLIENT_SECRET`, `YOUTUBE_REFRESH_TOKEN` directly in `.env`), never in the repo or an event; `upload` never sends anything but `private`, and a lost upload session stops and asks a person rather than uploading twice. Captions (`captions.en.srt`) and the YouTube-sized description are written by `npm run video -- package`; the full source list stays on the topic page.
- The working pages (production board, story ideas, scripts, the review page, the inquiry register at `/<topic>/register`, admin index) live in `src/admin/` and are routed only by the dev server (`astro.config.mjs` injects them when `command === 'dev'`); a build never emits them and links to them are guarded by `import.meta.env.DEV`. Only topics an institution claims (`commissions` in `src/config/site.ts`, `publicTopicNames()`) and, in them, only stories with a live video and what hangs off them are built; the dev server previews packaged stories too (`siteGraph` in `src/modules/website/site-graph.ts`, `View` in `content-graph.ts` beside it); the brand charter is `brand/`. The production board (`src/admin/Board.astro`, the Board, Stages, Pipeline and Artifacts tabs of `/admin`) shows one row per video in a sortable, filterable table, its state who acts next (`COLUMNS`, `columnOf` in `production.ts`; a follow-up has no row). Red in a row means only that `/produce` stopped (`revision-limit`, `story-left` or a `stop:` step); every other halt is its next step. The review page (`src/admin/review.astro`, `/<topic>/review/<folder>`, model in `src/modules/website/review-view.ts`) is rendered per request; its media (`src/admin/media.ts`) streams the packaged build from disk and its actions (`src/admin/review-action.ts`) refuse any other origin and any build but the current one, writing through the publish verbs or running the CLI as a job (`src/modules/website/review-job.ts`, `video/review-job.*`, gitignored).
- Shorts: a Short is a nested production, id `<story-id>/shorts/<slug>`, folder `scripts/<story slug>/shorts/<slug>/` (`shortOf`, `scriptDir` in `src/shared/io.ts`), never a story. `shorts.json` is derived (never hand-edited, byte-identical on a rerun); the judgment lives in `shorts-review.json`, keyed by candidate key (the scene's first sentence id); no candidate is ready without it, at most `MAX_SHORTS` (3) per video, and the parent must be locked. Its evidence package is a filter of the parent's (`buildShortPackage` in `src/modules/shorts/shorts.ts`) with a `short` block, never built from the store or the story; a Short never touches the store, the corpus, a verdict or `record-sources`. The block selects `SHORT_SECTIONS` (`hook`, `finding`, `close`), makes `scope` (a claim outside the package), an unplaced `needs-qualification` and a figure in `close` blocking, and caps the storyboard at `SHORT_MAX_SECONDS` (60; QA fails a measured Short over 180). The frame is `PORTRAIT` (1080x1920) laid out by `SHORT_LAYOUT` (`src/modules/video/types.ts`): the badge and format eyebrow above `top`, the content band, the caption band, the citation block ending above YouTube's overlay; a Short draws only with `SHORT_GENERIC` (`kinds.ts`, names `short-*`, chosen by `registryFor(pkg)`), in the institution's look (`theme`, faces embedded by `fonts.ts`, the badge, captions and backdrop in `remotion/Portrait.tsx`). A packaged Short records itself as the output `short:<slug>` in its parent's `publish.json` (`derivedFrom: youtube`, `source` its folder; `npm run publish` maps a short id to that entry); the related-video link has no API and is a Studio step the ledger records as `updated --fields relatedVideo`. A Short's board row sits under its parent's and is never the topic's next step.
- The workflow diagram on `/admin` (`flow` in `src/admin/index.astro`: who acts, what runs between) is the map a person follows. A change that adds, removes or reorders a stage, a human step or a halt a person resolves updates `flow` in the same commit; `planned` marks a step not built yet.
- Calculators (`src/tools/`, `toolOf`): a tool's defaults cite a dataset or a passage; `src/tools/**` holds no outbound link and no partner.
- Site navigation is a tree (Record, institution, inquiry, matter, with the data page beside its inquiry): every page below home has the `ReportHeader` trail to each level above (a phone shows only the parent), and lists everything below it. `/inquiries/` (the nav's first entry) is a list, not a level: every inquiry under its institution with its matters, so a visitor finds a topic in one click without the institutions being flattened. Every list of matters is `MatterList.astro` in `matterOrder` (`content-graph.ts`: a live video first). A link list that mixes kinds of destination (a matter, a video, an article, data, a tool, an inquiry, an outside page) marks each with `KindIcon.astro` from the `SourceIcons` sprite, its kind also said in text or an accessible label. The dist test walks the site from `/`: every page reachable, every matter within three clicks.
- `/privacy/`, `/terms/` and `/publishing/` (the OAuth consent screen's privacy policy, terms of service and homepage) are out of character, written by the real publisher, and every statement on them must stay true of the code; `/publishing/` is linked from `/privacy/` only. The site loads nothing from a third party: the brand faces are self-hosted from `brand/fonts/` (`@font-face` in `src/styles/global.css`), and `thirdParty` in `tests/web-quality.json` stays empty.
- Site pages are rendered at build time.
