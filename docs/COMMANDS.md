# Commands

The full description of every `npm run` verb, moved here from `CLAUDE.md` (which keeps one line per command and the
rules). The runbook by situation is `docs/OPERATIONS.md`. Each verb below says what it reads and writes; a verb that
talks to a service or pushes says so.

## Verification

- Verification is change-driven (Jon, 2026-11-01): while implementing, run the tests of the files and modules being changed; after a task, `npm run check` (incremental `tsc --noEmit` and the cached lint) plus the relevant tests, not the whole suite; after review fixes, the targeted regression tests and what depends on them; `npm run validate` (typecheck, lint, format check, build, tests: what CI runs on push) and the e2e rehearsal (`npm run rehearse`) once on the final candidate of a phase or branch, and again only when a later change could invalidate them (a fast-forward merge of the verified candidate is not re-validated). Coverage, the boundary test and the phase gates stay as they are; this trims repetition, not checks. `/produce` and the runner still validate before an automated commit (a gate on agent-written code, not iteration).
- `npm run quality` is the web-quality gate for site changes: build, the static gate and the browser suite (one page per template, Chromium); `-- --audit` runs every page in Chromium, Firefox and WebKit plus `npm audit`. Results in `.web-quality/`. Browsers: `npx playwright install chromium firefox webkit` once. `npm run test:browser` runs the browser project alone (the site suite and the admin live test, which starts its own dev server).
- `npm run format` fixes formatting (prettier with astro + tailwind plugins); `npm run format:check` only checks. `npm run typecheck` is `astro check`, `npm run typecheck:ts` is `tsc --noEmit`; `npm run test` is the unit project.

## Research and the record

- `npm run report [-- <topic>]` regenerates `topics/<topic>/report.json` (every topic with a store, or the one named: what the maintenance scan runs) and keeps `topics/<topic>/public-record.json` (exhibit numbers, for the sources of live claims only, that never renumber, and a revision for each claim whose finding label or verdict changed; it prints those that need a note). It needs the watcher checkout (`../retire-sim/watcher` or `$WATCHER_DIR`), so it only runs locally; commit the result, the site is built from it. `-- seed [topic]` numbers exhibits without the watcher; `-- note <topic> <claim> "<note>"` explains a revision.
- `npm run watcher -- <cmd> --store topics/<topic>/store` runs the watcher CLI. `npm run record -- <topic> <h.json> [--label] [--from <id>]` records an extraction batch; `npm run record-sources -- <topic> <sv.json>...` records study verdicts (never `--replace-cited` from automation); `npm run merge-claims` applies a merges file.
- `npm run evidence -- search "<query>" [--max 40] [--json] | fetch-doc <topic> <https url> <file.txt> [--pages a-b] | lists <topic> | groups <topic> | check-batch <topic> <work/hN.json> | check-verdicts <work/sv_N.json> | dedupe <topic> | check-merges <topic> | collide <topic> [--resolve] | thin <topic> [--json] | scanned <topic> --found n --recorded n` are the deterministic research verbs (`src/modules/evidence/cli-research.ts`, spec 5.2): `search` and `fetch-doc` are the only two a collect agent may run (read-only results; a document saved only under `topics/<topic>/sources/`, https, a bare `.txt` name); the rest are the topic runner's: groups for parallel extraction, exact duplicates to `n2`, collisions with the watcher's own similarity, the thinness that parks a topic (`topics.minSources`, `minStudies`, `minDecided`), the validators of the collect, extract, sources and merge briefs (`lists`, `check-batch`, `check-verdicts`, `check-merges`), and `scanned` (the maintenance record `topics/<topic>/maintenance.json`).
- `npm run topics -- validate [<slug>] [--review|--fresh] | show [<slug>] | context <key> | approve <slug> --by <name> [--note] [--via] | reject <slug> --by <name> --note <why> | park <slug> --why <text> [--by] | batch [--dry-run] | sent <batch id> --message-id <id> | claim <topic> <commission> [--force --by <name>]` keeps `proposals/<slug>.json` (`src/modules/topic-discovery/`, spec 5.1): an agent proposes (`briefs/discover.md`, one new file per proposal), an independent agent reviews (`briefs/proposal-review.md`, `<slug>.review.json`), code validates and ranks, `batch` parks the weak with the reviewer's reason and lists the strong per institution under one `pb-` id, and only a person approves or rejects (`automated:` refused; idempotent). A proposal never writes under `topics/`; the approved ones are what the research pipeline starts from. `claim` adds the topic to its commission's line in `src/config/site.ts`.

## Stories, scripts, articles

- `npm run stories -- discover <topic>` regenerates `topics/<topic>/stories.json` (story candidates with their evidence audit), merging `topics/<topic>/story-review.json` if present; it reads the report and store, so it runs anywhere. Commit the result. `validate <topic> <assertions.json>` is the evidence gate. The review file is the agent's semantic pass (`src/modules/stories/briefs/stories.md`): applicability of each verdict to a sentence, coherence and pruning of each candidate, viewer-facing framing.
- `npm run script -- run <topic> <story-id>` drives the script stage in `topics/<topic>/scripts/<slug>/`: `package` builds the evidence package from stories.json and the store, `validate` checks `script.json` (written by an agent from `src/modules/script/briefs/script.md`) and merges `script-review.json` (written by a different agent from `src/modules/script/briefs/script-review.md`), `storyboard` fills and checks `storyboard.json` (from `src/modules/storyboard/briefs/storyboard.md`); `show` prints the reviewer's sheet; `lock --approved-by "<name>"` writes `release.json` once validation is `passed`, the storyboard `ok` and a render check it re-runs is ok with every bespoke graphic approved; it refuses any approver containing a `<...>` placeholder. `send-back <topic> <story-id>` opens a notes pass on the script (`passStartRevision`). Commit the directory.
- `npm run article -- validate|show|frames|lock|correct|reaffirm|request-correction|decide|sent <topic> <story-id>` drives the companion article in `topics/<topic>/scripts/<slug>/` (`src/modules/article/`: `article.ts`, `validation.ts`, `view.ts`, `request.ts`, `cli.ts`; its briefs are `src/modules/article/briefs/`): `validate` checks `article.json` (the script checks over its sentences, plus coverage, metadata, tables, figures and overlap with the narration) with `article-review.json` against the story's evidence package, writing `article-validation.json` and `article.md` and printing `RESULT:`; `show` prints `article.md`; `frames [--port <n>]` validates afresh, starts the dev server in-process and photographs the matter page as it renders the validated draft (375 and 1280 wide, light and dark, tiles 1000 px tall under `page/`, with `index.json` naming the article fingerprint the page carried; refused when the page did not render that text); `lock --approved-by "<name>"` writes `article-release.json` (the snapshot the site renders) once a review exists and a fresh validation passes; `correct --approved-by "<name>" --note "<note>"` releases changed text and appends an article revision (the changed sentence ids and the note) to `public-record.json` (once: a re-run finds it there); `reaffirm --approved-by "<name>" --note "<why unchanged>"` keeps a stale article's unchanged, passing text, adding a history entry and moving the release date to today (no public-record revision); `request-correction --by` writes `article-request.json` (an `ar-` id signed with `APPROVAL_SECRET`, bound to `article.json`'s fingerprint; it needs a review and a passing validation, reuses an open request for the same text, voids on a changed one); `sent --request <ar-id> --message-id <id>` records the request mail's Message-ID (idempotent; a different id for a sent request is refused); `decide --request <ar-id> --verdict ok|changes --by "<name>" [--note ...]* [--via <channel:id>]` is a person's answer (never `automated:`): `ok` is `correct` for that exact fingerprint by that person, `changes` records the notes for the next writer pass. The reviewer approves the headline, SEO title, headings, tables and figures by unit id at the fingerprint `show` prints, as sentences. Refusals exit 2 and write nothing.

## Video, music, Shorts, brand

- `npm run video -- spike <topic> <story-id>` renders `topics/<topic>/scripts/<slug>/video/segment.mp4` from `video/render.json` (scenes, voice, cues, bespoke kinds, options, chapters): narrate (edge-tts draft or openai commercial, cached per sentence), timeline (measured audio, not the word-count estimate), render (Remotion, one cached chunk per scene, concatenated, narration track laid down with loudnorm, the soundtrack from `video/music.json` mixed under it into `video/mix.json`), qa (build-report.md, frames/, contact-sheet.png). `render --scene sc17` renders one scene with audio into `video/scenes/`. `package` writes the private review package to `video/review/`. `preview` opens the Remotion studio. Commit the JSON and the report, never the media.
- `npm run video -- final <topic> <story-id> --approved-by "<name>"` is the release build: development always narrates with `edge` (draft only); once a person accepts the draft package, `final` re-narrates the same words with `azure` (the same neural voice under commercial terms, keys in the gitignored `.env`; the key is read only by the narration worker `npm run tts-azure`, a process per sentence that loads `.env` itself and imports no renderer code, while the video CLI forgets `AZURE_*` right after loading `.env`, so no process that loads agent-written components ever holds it), then re-runs timeline, render, qa and package in place. It refuses a story the board does not say is `packaged`, a placeholder approver, or a failed QA. The approver is recorded in the build report's command line. A cleared build packages as the release build (`status: release build` in `review.json`: `<slug>.mp4`, the real title, no private banner, voice line or draft-voice check); a draft build keeps the private review package. Both are the same `video/review/` folder and the board tells them apart by the report's clearance.
- `npm run video -- init <topic> <story-id> [--force]` drafts `video/render.json` from the storyboard (never overwrites without `--force`); `check` writes `video/render-check.json` (renderability, diagrams without a graphic, each bespoke graphic's approval in `video/visual-review.json` at its key); `frames --scene <id>` renders one scene on its own into `video/frames/<id>-start|mid|end.png`. QA, spike and a full render end with `RESULT: PASSED` or `RESULT: FAILED (...)`.
- `npm run music -- cues <topic> <story-id> [--composition <id>] [--force]` drafts `video/music.json` from the script's sections over a cleared composition. `npm run music -- import|render|show <composition>` keeps `music/<composition>/` (compositions rendered by strudel-bench; `music/README.md` is the contract, `src/modules/video/briefs/strudel-bench.md` the handoff to that repo).
- `npm run shorts -- discover <topic> <story-id>` writes `topics/<topic>/scripts/<slug>/shorts.json`: one Short candidate per storyboard scene of a produced video whose sentences are verified and approved and that asserts a fact, merged with the reviewer's `shorts-review.json` (`src/modules/shorts/briefs/shorts.md`: keep, slug, format, hook, how each qualification is carried). `show <topic> <story-id> [key]` prints a candidate with its passages. A ready candidate is produced as `<story-id>/shorts/<slug>` through the same CLIs as a video (`script`, `video`, `board next`, `/produce`, `publish`).
- `npm run brand` writes every brand kit into `brand/<brand>/` (SVGs committed, PNG/JPG rasters gitignored) and the site's seals `public/commissions/<key>.png`, from `src/modules/brand/draw/draw.js`, each `kit.json` and `src/config/site.ts`, fitting text in the brand fonts in Remotion's headless Chrome. Re-run after changing a drawing or a kit; it also writes the site's share cards (`public/og/`, one per public story in `public/og/stories/`, so re-run it when a story's question changes), seals (`public/commissions/`), stamps in both inks (`public/stamps/`, shown by `src/components/Stamp.astro`), favicon set and header logo.
- `npm run packaging -- package|manifest <topic> <story-id>` is packaging's own CLI (`npm run video -- package` reaches it); `manifest` rewrites `video/review/release-manifest.json` from the files without media (the article lock calls it).

## The board, the runner, the planes

- `npm run board -- next <topic> <story-id> [--json]` prints the board's stage, next step, steps and halt kind for one story; `npm run board -- topic <topic> [--json]` the research board's (`topicNext`); `.claude/skills/produce/SKILL.md` (`/produce`) loops on `next` from `ready` to `packaged`.
- `npm run run -- story <topic> <story-id> [--approver "<name>"] [--until <stage>] [--model <alias>] [--notes-file <path>] [--fresh] [--no-commit]` is that loop as code (`src/orchestration/run/`): the board's steps run as child processes and `claude -p` agents, journaled under the story's gitignored `run/` (one attempt record per agent call under `run/agents/`), locked per story, capped and budgeted by `automation.json`; a crashed run resumes with the same command (exit 0 done, 1 halted with `HALT <kind>` and `UNBLOCK`, 3 held by a live run). `--model` sets every role's model for the run (a cheaper alias for a supervised fixture run; the attempt records keep the alias and the model version the CLI reports). `status [--json]` lists every run, halt and unblock. `tick [--preflight]` is the control plane (one short pass: preflight, outbox, inbox, due publications, deploy probes, due resumes, stuck runs, halt emails, digest; never a story; `--preflight` runs the preflight alone as if `enabled.tick` and `enabled.work` were on, prints it and writes nothing), `work [--job <kind>] [--dry-run]` the work plane (one long job per instance: a launch, a resume, a release loop, the production pick, a discovery, a topic run, a scan; the scheduled task is `work --job launch`, launches only, one instance at a time, so no agent-written code runs unattended; the locks are the bound when a person starts jobs by hand), `pick [--dry-run]` the production pick by hand, `schedule --print` the two scheduler commands (both "Do not start a new instance") and the power lines (never run here); long work never runs inside the tick. A fixture story takes `--fresh`; a supervised run on a feature branch takes `--no-commit`.
- `npm run publish -- correct-actor <topic> <story-id> --event-at <ISO> --actor "automated: <what>" --note <how it is known> [--output <id>]` records who really ran a verification that names someone else: the event stays as written and a person's approval, decision or go-live is refused.
- `npm run run -- probe <topic> <story-id>` is the tick's deploy step for one launch by hand (the page read once; live and carrying the video, the video's `go-live` under the person's `decided ok` and a `verify`; then, once the video is verified and every uploaded Short is live, the social step by policy and the launch mail, once each); `npm run run -- settle <topic> <story-id> [--by <actor>]` clears an `awaiting-person` halt older than its output's publication or the person's `decided ok`, on the story and its Shorts, drops its queued resume and keeps the halt in the journal (the tick does the same).
- `npm run run -- maintain <topic>` is the maintenance scan by hand (what the work plane's `scan` job runs every `schedule.maintenance.everyDays` days per public topic with `enabled.maintenance`): a `new-sources.md` agent, `record-sources`, `npm run evidence -- scanned <topic> --found n --recorded n` (the record `topics/<topic>/maintenance.json`), `report`, a `revision-note.md` note per revised finding, `stories discover`, validate, one commit, then the article pass; `clear <topic> <story-id>|research --by "<name>"` clears a story's `needs-person` halt (a live video citing a revised finding).
- `npm run run -- topic <topic>` is the research pipeline for one approved proposal (`src/orchestration/run/topic-runner.ts`; the work plane runs it for an approved proposal not yet researched, only with `enabled.research` on and under `runs.maxConcurrentTopicRuns`): the loop over `topicNext` (`src/orchestration/research.ts`), the research agents under their role grants (extraction and judging in parallel up to `maxParallelAgents`), every store write a child CLI (`record` serial and resumed with `--from`; `record-sources` never with `--replace-cited`), the markers under `topics/<topic>/work/run/` (recorded batches and judged documents, study and review rounds), a thin or storyless topic parked with `topics -- park` (no halt), the finish validated and committed on main, staging only what the run's own steps wrote (the guard's diff after each step, less anything dirty before the run; the claim's own line of `site.ts`); a file a person adds or edits between steps is left out of the commit, kept on disk and named in the finish line, and a hand edit to a path the run wrote halts `git` with nothing staged. A crashed run resumes with the same command.
- `npm run run -- discover [--institution <key>] [--dry-run]` is the weekly topic discovery by hand (costs agents); `npm run run -- launch <topic> <story-id>` the launch job by hand (what the work plane runs once a person decided `ok` on the approved video, so the matter page is deployed with the video before it goes public, or once a scheduled video is live and verified): `report -- seed`, `brand`, `build`, `links freeze`, `validate`, one commit, one push, resumable from `.automation/launch/`; a finished launch is run again when the video is decided again before it went live.
- `npm run run -- verified <integration> --by "<name>" --evidence <ref>` records a person's verification of one integration in `readiness.json` (its only writer): the evidence must name a record of the kind that proves that integration (`INTEGRATIONS` in `src/orchestration/run/readiness.ts`: a ledger event of the named type, a reply decision with `via: email`, a `<Message-ID>` the outbox sent or the inbox applied, `scan:<topic>`, `shadow:<topic>/<story>`, `launch:<topic>/<story>`, `social:<topic>/<story>`, `tick:<ISO>`, `run:<id>` of a finished topic run, `discovery:<slot>`); an automated actor, a dangling reference and a record of another kind are refused; no flag changes.

## Publishing, social, the site

- `npm run mail -- ask "<subject>" --text "<question>" [--about <ref>] [--reply-to <qn-id>] [--timeout <minutes>] [--poll <seconds>]` asks the approver by email and blocks until the reply (`ASKED`, then `ANSWER` and the person's words, exit 0; `NO ANSWER`, exit 1, the question stays open); `ask --resume <qn-id>` waits again; `questions [--about <ref>] [--status <s>] [--unseen] [--fetch] [--json]` lists them and the replies that matched nothing; `questions --ack <qn-id> [--note "<what was done>"]` accepts an answer; `questions --close|--reopen <qn-id> --note "<why>" [--by <who>]` closes a question nobody will answer (out of every open list, archived as completed, a later reply kept but never acted on) or reopens it; `report "<subject>" (--text "<t>" | --text-file <path>) [--about <ref>]` sends a one-way completion report that opens no question; `test [--await-reply]` is one round trip (external effect); `init [--dry-run]` migrates the legacy outbox; `send --file` and `fetch` are what orchestration runs as children. The module's usage header in `src/modules/mail/cli.ts` has every flag.
- `npm run publish -- <verb> <topic> <story-id> [--output <id>]` keeps the publishing ledger `topics/<topic>/scripts/<slug>/publish.json` (`src/modules/publishing/`, ledger in `publish.ts`): `show`, `uploaded --id`, `approve --by`, `thumbnail <file>`, `scheduled --at`, `published`, `updated --fields`, `failed --step --error`, `unpublished`, `retracted`, `add <output-id> --kind`, `accept-draft --by --build` (the draft acceptance `video final` records; never a publication approval; a draft is a draft-voice build; `--dry-run` checks without writing), `request-changes --by --note [--at <seconds>] [--scene <id>] [--sentence <id>]` (sends the current build back with placed notes), `request --channel email [--renew]`, `message-sent --request --message-id`, `decide --request <id> --by <name> --verdict ok|schedule|changes [--at <ISO>] [--note ...]* [--paid <cta id>]* --via <channel:id>` (`ok` approves and leaves the video private for the tick's go-live after the page is deployed; `schedule` hands YouTube the time). Every verb is idempotent (an existing key prints the event, exit 0) and refuses with exit 2 without writing. The API verbs (`uploader.ts` over `youtube.ts` in the same module, plain `fetch`, no googleapis) write the same events: `auth [--commission <key>]` (one-time consent), `upload` (always private, with thumbnail and captions, resumable through `video/upload-session.json`; refused before any byte unless the authenticated account's channel is the commission's `YOUTUBE_CHANNEL_ID_<KEY>`, or `YOUTUBE_CHANNEL_ID`, in `.env`), `push` (changed metadata), `go-live [--at]` (public or scheduled; needs the ledger's `approved`; a fixture topic goes unlisted at most), `sync` (read back), `verify` (read back and compare with the package; records `verified`). The hand verbs remain the fallback.
- `npm run social -- show|compose|post <topic> <story-id> [--output <id>] [--dry-run]` posts about a live output from the owning institution's X account (`src/modules/social/`, record `social.json` beside the ledger): `post` refuses while `automation.json` `enabled.social` is off or the output is not live, prints `not configured` (exit 0) when the institution has no X handle or keys (`X_<KEY>_*` in `.env`), posts the same text once (an intent record before the call, the id after, a crash reconciled from the account's recent posts), and never posts a fixture from a public account.
- `npm run links -- freeze` writes `public-urls.json` (every indexed page in `dist/`; run after `npm run build`, commit it); `check` requests every outside URL the built site and the committed descriptions link (local and networked, never in CI; exit 1 on a failure); `live <topic> <story-id>` is the deploy probe (one request: `RESULT: LIVE` or `NOT LIVE (<why>)`); `cta <topic> <story-id>` shows the destinations and checks `cta.json`; `cta approve <topic> <story-id> <cta id> --by "<name>"` writes a person's approval of one paid link into `cta.json`.
- `npm run rehearse -- <topic> <story-id> [--keep]` rehearses a go-live in a throwaway copy of the working tree (the real checkout is never written) and runs the web-quality gate against the result; `npm run dev`, `build`, `preview` are Astro's; `npm run stop` is Astro's `dev stop` (ends the dev server it started; an orphaned server from an earlier session is killed by hand, by its port).
